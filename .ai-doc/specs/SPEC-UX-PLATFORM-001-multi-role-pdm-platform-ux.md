# SPEC-UX-PLATFORM-001: 多角色 AI PDM 平台 UX 架構優化

狀態: Phase 1A/1B Implemented；Phase 3 自適應任務路由另列 `DEV-UX-PLATFORM-002`
日期: 2026-06-02
專案: AI_PDM
文件類型: PM / UX 架構規格
適用範圍: AI PDM Web 平台資訊架構、工作台、導覽、物件頁、任務路由與跨角色工作流

## 1. 文件目的

目前 AI PDM 已具備上傳送審、BOM 工作台、BOM 審核、領號申請、DVT 晉升、圖料查詢、MA 影響分析、圖號待辦、總表匯入、圖號報表、製造交接、系統設定等功能。

現有 UX 問題不是單純「功能太多」或「選單需要重排」，而是平台正在從 RD 工具擴張為跨部門 PDM 平台。若仍以固定功能列表作為主要入口，未來 QA、QC、PM、製造、採購、供應商、管理者加入後，會產生導覽複雜度外溢、工作流斷裂與新人學習成本升高。

本文件定義下一階段 UX 優化方向:

- 以多角色使用者為對象，不再只以 RD 工作流設計首頁與導覽。
- 以物件生命週期和個人任務為核心，降低使用者理解成本。
- 讓平台可隨角色、權限、流程狀態與功能模組擴充，而不需要不斷堆疊 sidebar 入口。
- 提供可交付、可驗證、可分階段實作的 UX 架構。

## 2. 調用思考習慣

本規格使用以下思考習慣作為設計依據:

- #最佳化: 最佳化目標不是曝光最多功能，而是讓每個角色用最短路徑完成下一步。
- #設計思考: 從角色、任務、痛點、決策情境出發，再決定入口與畫面。
- #系統動力學: 預防平台擴充後的複雜度外溢，讓導覽與任務能隨系統規模自我收斂。
- #受眾: 同一功能在不同角色眼中代表不同任務，不能只用 RD 語言命名。
- #系統地圖: 將專案、圖號、料號、BOM、變更、審核、驗證、交接、報表串成可理解的生命週期。

## 3. 現況問題

### 3.1 功能以模組平鋪

目前 sidebar 近似功能清單。使用者需要先知道每個功能名稱代表什麼，才能判斷要去哪裡。

風險:

- 新使用者無法快速判斷從哪裡開始。
- 跨角色使用者看到大量與自己無關的入口。
- 功能越多，sidebar 越難維護。
- 相似功能容易重複出現，例如待辦、審核、報表、查詢散落在不同模組。

### 3.2 UX 偏 RD 工程流程

既有設計多以 RD 的設計送審、BOM、DVT、發行為核心。但平台擴充後，使用者會包含:

- RD / 工程師
- QA / QC
- PM / 專案管理
- 製造 / 生產導入
- 採購 / 外包管理
- 供應商 / 外部協作
- 管理者 / 主管
- IT / 系統管理者

若首頁只用 RD 任務架構，其他角色會覺得平台不是為自己設計的。

### 3.3 使用者需要的是下一步，不是全部功能

多數使用者進入系統時不是想探索功能，而是想知道:

- 我現在有什麼待辦?
- 哪些東西卡住?
- 我負責哪個流程節點?
- 我要查哪個物件?
- 這個物件下一步是什麼?
- 缺什麼資料、審核或證據?

因此 UX 的主要任務應是「路由工作」，不是「展示功能」。

## 4. 設計目標

- 讓不同角色在 30 秒內找到自己的工作入口。
- 讓使用者可以從物件、任務、流程、搜尋四種路徑進入系統。
- 讓 sidebar 從功能堆疊改為平台導覽，不承擔完整教育責任。
- 讓首頁從 RD 指揮台改為多角色工作台。
- 讓每個物件頁承載狀態、關聯、歷程、證據、待辦與下一步。
- 讓未來新增角色或功能時，只需新增任務類型、物件類型或角色視角，不必推翻資訊架構。

## 5. UX 方案比較

### 方案 A: 角色工作台

每個角色有自己的首頁與任務排序。

適合:

- 角色任務差異很大。
- 權限與職責清楚。
- 需要降低新人學習成本。

優點:

- 使用者一進來就看到與自己相關的任務。
- 審核者、製造、PM、管理者不會被 RD 功能淹沒。

缺點:

- 角色越多，工作台維護成本越高。
- 若使用者跨角色工作，可能需要頻繁切換視角。

### 方案 B: 物件中心 UX

以核心物件作為主要入口:

- 專案
- 料號
- 圖號
- BOM
- 變更單
- 審核任務
- 驗證證據
- 交接包

每個物件頁固定呈現:

- 摘要
- 狀態
- 關聯資料
- 待辦
- 歷程
- 文件 / 證據
- 下一步

優點:

- 最符合 PDM 本質，因為 PDM 是物件、版本、關聯與生命週期治理。
- 同一個圖號或 BOM 可被 RD、QA、製造、PM 用不同角度理解。
- 平台擴充時可新增物件類型，而不是新增大量選單入口。

缺點:

- 首頁搜尋、最近使用、關聯導覽必須做得好。
- 需要建立一致的物件頁模板。

### 方案 C: 流程地圖 UX

以產品生命週期作為主視圖:

```text
需求 / 專案 -> 領號 -> 設計 -> BOM -> 審核 -> DVT -> 發行 -> 製造交接 -> 變更 / 汰除
```

每個節點顯示:

- 待辦數
- 卡關數
- 負責角色
- 缺失資料
- 下一個 gate

優點:

- 跨部門最容易理解整體進度。
- PM 與管理者可快速看瓶頸。

缺點:

- 對只想查一張圖或處理單一待辦的使用者太重。
- 流程圖不適合承擔所有日常操作。

### 方案 D: 自適應任務路由

首頁依角色、權限、最近行為、任務狀態、逾期程度與關注物件動態排序。

首頁區塊:

- 我的待辦
- 我關注的物件
- 最近處理
- 系統建議下一步
- 跨部門阻塞
- 常用工具

優點:

- 最符合多角色長期平台。
- 使用者不需要理解全部功能即可處理工作。
- 可隨平台成長自我收斂。

缺點:

- 需要定義任務權重、排序規則、摘要資料與空狀態。
- 初期實作比單純重排選單複雜。

## 6. 推薦方案

推薦採用「方案 B + 方案 D 為核心，方案 A / C 作輔助」。

也就是:

> 以物件為中心，以任務路由為首頁，以角色視角做篩選，以流程地圖做全局理解。

### 6.1 產品定位

下一版不應命名為 RD 工作台，而應定位為:

> AI PDM 工作台: 以物件生命週期與個人任務為中心的多角色平台。

### 6.2 首頁定位

首頁是工作路由器，不是功能入口集合。

首頁應回答:

- 我現在該處理什麼?
- 我關注的物件發生什麼變化?
- 哪些流程卡住?
- 哪些工作快逾期?
- 我最近處理過哪些物件?
- 我可以從哪裡快速搜尋或建立工作?

### 6.3 Sidebar 定位

Sidebar 是平台地圖，不是全部功能清單。

建議主導覽:

- 工作台
- 專案 / 圖料
- BOM
- 變更 / 審核
- 驗證 / 品質
- 發行 / 交接
- 報表
- 設定

功能入口可作為各區域內的 action，而不是全部攤在 sidebar 第一層。

## 7. 目標資訊架構

### 7.1 工作台

目的: 統一承載個人任務、關注物件、阻塞與系統建議。

主要區塊:

- 我的待辦
- 最近物件
- 關注物件
- 跨部門阻塞
- 系統建議下一步
- 快速建立 / 快速搜尋

### 7.2 專案 / 圖料

目的: 查詢與管理圖號、料號、文件、版本與關聯。

主要入口:

- 圖料查詢
- 領號申請
- 上傳送審
- 圖號總表匯入

### 7.3 BOM

目的: 建立、編輯、比對、審核與發行 BOM。

主要入口:

- BOM 工作台
- BOM 審核
- BOM 匯出
- BOM where-used / diff

### 7.4 變更 / 審核

目的: 管理 DVT、發行審核、ECR/ECO/ECN 與例外決策。

主要入口:

- 圖號待辦
- DVT 晉升
- 發行審核
- 變更申請
- 審核矩陣

### 7.5 驗證 / 品質

目的: 承載 QA/QC 驗證計畫、證據、缺失與品質風險。

主要入口:

- 驗證計畫
- QC 驗證報告
- 證據缺口
- 品質阻塞
- 放行條件

第一階段若產品尚未有完整 QA/QC UI，可先設為首頁工作台中的未來模組與報表入口，不必強行新增空頁。

### 7.6 發行 / 交接

目的: 將 Released 圖料、BOM、文件與證據轉成製造或外部協作用交接包。

主要入口:

- 製造交接
- 交接包檢查
- 外部分享
- 採購 / 供應商同步

### 7.7 報表

目的: 跨角色追蹤狀態、瓶頸、品質風險與稽核資料。

主要入口:

- 圖號報表
- 審核負載
- 逾期待辦
- 阻塞清單
- 品質 / 證據缺口

## 8. 物件頁模板

每個核心物件頁應使用一致結構，降低跨角色學習成本。

通用模板:

- 摘要: 名稱、編號、版本、狀態、負責人。
- 狀態: 生命週期階段、目前 gate、阻塞原因。
- 待辦: 與此物件相關的任務與通知。
- 關聯: 專案、圖號、料號、BOM、變更、交接包、證據。
- 文件 / 證據: 檔案、報告、審核記錄、驗證資料。
- 歷程: 建立、修改、審核、發行、退回、汰除。
- 下一步: 系統依角色和狀態推薦可執行動作。

角色差異不應改變物件頁結構，只改變可見資料、動作與排序。

## 9. 任務路由模型

### 9.1 任務來源

任務可來自:

- 圖號申請
- BOM review
- DVT promotion
- Release gate
- ECR/ECO/ECN
- QA 驗證缺口
- QC 驗證失敗
- 製造交接缺件
- 採購 / 供應商回覆
- 系統設定或權限待處理

### 9.2 任務摘要欄位

任務卡至少包含:

- 任務標題
- 物件類型與物件編號
- 負責角色 / 負責人
- 風險等級
- 截止時間或逾期狀態
- 建議下一步
- 主要 action URL

### 9.3 任務排序原則

排序優先級:

1. 阻塞 release、製造交接或客戶承諾的任務。
2. 已逾期或即將逾期的任務。
3. 指派給我的任務。
4. 我關注物件的狀態變更。
5. 最近處理流程的下一步。
6. 一般通知與資訊。

## 10. 首頁設計規格

首頁名稱: 工作台

主要區塊:

- 全域搜尋: 支援圖號、料號、BOM、專案、交接包、變更單。
- 我的待辦: 依風險和時間排序。
- 系統建議下一步: 根據角色、權限、狀態、最近行為推薦。
- 關注物件: 顯示最近變更、卡關、待審、交接缺口。
- 跨部門阻塞: 顯示責任角色、缺口原因、影響範圍。
- 常用工具: 依角色和使用頻率顯示，不固定。

首頁不應顯示所有功能。首頁應顯示「此刻最有價值的下一步」。

## 11. Sidebar 設計規格

### 11.1 第一階段 Sidebar

第一階段可先使用以下結構:

```text
工作台
專案 / 圖料
BOM
變更 / 審核
驗證 / 品質
發行 / 交接
報表
設定
```

若技術上短期仍需保留現有頁面直連，可在群組內使用二級連結。

### 11.2 Sidebar 原則

- 第一層不超過 8 個主類別。
- 第一層用平台語言，不用單一部門語言。
- 第二層才放具體功能。
- 權限過濾後不應留下空群組。
- 手機版可壓縮成橫向類別或抽屜式導覽。

## 12. 分階段交付

### Phase 1: 導覽與首頁收斂

目標: 先降低目前使用者的找功能成本。

交付:

- Sidebar 改為平台分群。
- 首頁改名為工作台。
- 首頁新增我的待辦、最近物件、快速搜尋、常用工具。
- 現有頁面入口保留，但不再全部平鋪。

不做:

- 不新增資料表。
- 不改核心 API。
- 不建立完整自適應任務引擎。

### Phase 2: 物件頁標準化

目標: 建立可支撐多角色使用的物件中心 UX。

交付:

- 圖號 / 料號物件頁模板。
- BOM 物件頁模板。
- 交接包物件頁模板。
- 每個物件頁顯示狀態、關聯、待辦、歷程與下一步。

### Phase 3: 任務路由與角色視角

目標: 讓首頁依角色、權限和狀態動態排序。

交付:

- 任務摘要模型。
- 任務排序規則。
- 角色視角篩選。
- 關注物件與最近物件。
- 跨部門阻塞摘要。

### Phase 4: 流程地圖與管理視角

目標: 支援 PM、管理者與跨部門協調。

交付:

- 生命週期流程地圖。
- gate 狀態摘要。
- 逾期與瓶頸報表。
- 部門負載與品質風險視圖。

## 13. 驗收標準

### 13.1 使用者體驗驗收

- 新使用者可在 30 秒內理解主要入口。
- RD 可在首頁找到送審、BOM、退回修改、DVT 相關工作。
- QA/QC 可在首頁找到驗證缺口、證據、品質阻塞與放行條件。
- PM 可在首頁或流程視圖看到跨部門卡點與逾期風險。
- 製造可快速找到 Released 圖料與交接包。
- 管理者可看到瓶頸、逾期、審核負載與高風險項目。

### 13.2 系統擴充驗收

- 新增角色時，不需要新增 sidebar 第一層入口。
- 新增功能時，優先掛到物件頁、任務路由或二級功能。
- 新增物件類型時，可沿用物件頁模板。
- 權限過濾後導覽仍然完整，不顯示空群組。

### 13.3 UI 驗收

- 桌機、平板、手機皆不發生文字重疊。
- Sidebar 第一層不超過 8 類。
- 首頁不出現所有功能攤平的入口牆。
- 空狀態必須提供下一步行動。
- 完成動作後必須提供合理下一步。

## 14. 風險與對策

| 風險 | 影響 | 對策 |
|---|---|---|
| 過早導入完整自適應任務引擎 | 工期變長，規格不穩 | Phase 1 先用現有 API 與靜態分群，Phase 3 再做任務排序模型 |
| 角色視角過度客製 | 維護成本升高 | 以物件頁模板為主，角色只改排序、可見動作與篩選 |
| Sidebar 分群後使用者找不到舊功能 | 短期學習成本 | 保留搜尋、常用工具、最近使用與舊功能二級連結 |
| QA/QC 模組尚未完整產品化 | 驗證 / 品質區域空洞 | 初期以證據、報告、阻塞摘要呈現，不新增空頁 |
| 管理視角需要跨模組資料 | 報表延後 | Phase 4 再導入流程地圖與管理報表 |

## 15. 建議下一步

- 建立 DEV task: Phase 1 導覽與首頁工作台收斂。
- 建立 QA 驗證計畫: 多角色入口、sidebar 權限、手機版導覽、首頁任務理解度。
- 盤點現有頁面可歸屬的主類別與二級功能。
- 定義物件頁模板的第一批適用物件: 圖號 / 料號、BOM、交接包。
- 定義任務摘要資料來源: numbering tasks、notifications、BOM reviews、submission status、handoff readiness。

## 16. 開放問題

- 是否要支援使用者自行設定「我的工作台」區塊順序?
- 角色視角是否由登入角色決定，或允許具備多角色權限者手動切換?
- QA/QC 的驗證 / 品質模組第一階段要做成正式頁面，還是先以報表與阻塞摘要呈現?
- 供應商 / 外部協作者是否進入同一套平台導覽，或使用獨立外部入口?
- 管理者流程地圖要以專案、產品線、客戶或 release gate 作為主要分組?
