### 背景工作與已提交事件：不把 worker 當成登入的人

1. 同步人類 command 從 verified principal 到 mutation／audit／receipt／outbox 保持不變；序列化只保存受控 actorBinding 作追溯，不序列化 authorizationActor、cookie或可重用登入證明。每次人類重新執行仍驗 current session／authority，不能把 payload actorBinding 當 bearer credential。切換期的既有 legacy mapping 只能核對命令已確定的 principal/profile pair；即使在 SQLite 開發路徑，也不得以 mapping 的值覆寫命令 principal。`principal_active` 不讀此 mapping。
2. Outbox delivery 是運送已提交事實；publisher 以既有 workload credential、已存 event／idempotency key 執行既定 delivery，不要求原 browser session 尚存，也不因原使用者 logout 丟棄應送事件。actorBinding 必須原樣傳遞、不能改成 worker principal；接收端若要執行新的業務動作，依其自己的受控命令授權，不把事件裡的 principal 當新登入。
3. 現有 recognition worker 只在已 claim 的 job／company／source fingerprint 範圍讀檔、heartbeat與完成 extraction；沿既有 worker authentication、lease與結果驗證。技術結果不是人類對 BOM／編號／權限的正式提交。正式採用／handoff仍經人類 API 取得 current verified actor；原使用者退出後可完成技術 job，但失效 session 不可藉 worker 正式提交。技術 audit 記 workload actor；可證的原人類 initiator另列追溯，缺歷史證據就保留未知，不能由 created_by／email 猜 principal。

**2026-09-25 唯讀 owner preview 執行切片。** `scripts/dev121-production-principal-cutover-preview-runner.mjs` 從 AI-PDM 既有 release bucket 的固定 operation prefix 讀 SHA-256／CRC32C／generation 綁定輸入，核對 exact Production project／region／database／application、image source revision、最多32個profile及每個profile的完整已列 provider alias set；不接受 email 作配對。它以既有 migrator identity 在單一 `REPEATABLE READ READ ONLY` 交易取得 DB 時間，重讀本地、Platform 與 OrgMaster 正式資料契約，輸出 local／producer／graph／workspace shadow／source hashes，再於固定 receipt prefix 寫 immutable `READ_ONLY_PREVIEW`；未知完成狀態先讀回同 operation receipt，精確相符才重播，衝突拒絕，不重做資料庫preview。receipt 明示 `sourceBindingsAttested=false`、`applyAllowed=false`：operation 提供的三 owner revision／manifest hash 目前只驗格式，尚未經各 owner provider readback 證明；preview 即使 workspace status 為 pass，也不可作 apply 授權。舊架構只留過渡與歷史稽核用途，不能因這個讀取器成為永久 runtime bridge。隔離 PostgreSQL schema／ACL QC 21/21、owner runner 3/3、TypeScript及scoped ESLint PASS，task-owned cluster／port／temp 已清理；Production Job、正式來源綁定、完整 resource／delegation shadow、原子 apply 與 L4 仍未執行。

本機新增`requireCurrentPrincipalCutoverSource`，以prepare封存的cohort／input／source hash作為固定輸入；僅在owner migrator的READ COMMITTED write transaction使用。它先序列化operation、處理已成功的同輸入replay，否則取得固定本地relation locks，重新讀完整local／producer事實與plan，重算封存值；workspace shadow非PASS或任何封存差異均在寫入前拒絕。來源時間以UTC正規化，避免連線預設時區造成偽漂移。函式回傳同connection且不可變的verified object；materializer不接受自行拼造或複製的來源。隔離PostgreSQL 17/17驗scope rule的真實來源拒絕、無漂移、catalog變更後拒絕、整筆commit／rollback／CAS衝突與unknown-outcome receipt replay，臨時叢集已清理。此函式只做**workspace層**behavior shadow；project/resource／delegation完整等價及revision／manifest正式來源驗證仍缺，不能把它當成切換已完成。

**切換transaction與防舊writer。** `scripts/dev121-principal-cutover.mjs` 的owner流程提供 register-inventory／prepare／readback／apply／replay，DB 存取沿既有owner runner。切換的來源重驗與寫入留在AI-PDM owner migrator的**同一個 READ COMMITTED transaction-bound client**，由`requireCurrentPrincipalCutoverSource`及`materializePrincipalCutoverInOwnerTransaction`負責；065只提供表、FK、trigger及最小權限，不另複製一套source／policy evaluator為DB cutover函式。入口檢查isolation與完整locks，非此模式在寫入前拒絕，caller重開正確transaction。這取代前輪「SERIALIZABLE 等鎖後即為 current」的假設；provision保持SERIALIZABLE，principal人類業務命令依下方單一授權讀點使用至少RR，不套用cutover的RC/table-lock策略。

apply 先對 operation_id 序列化並用下一個 SQL 查成功 receipt；同 input 已提交即回原結果與另列 current readback，不重跑 target preflight。無紀錄才取 sorted cohort locks，再按固定次序對本地來源、目的與 fence 狀態 tables 取 `SHARE ROW EXCLUSIVE` locks：cutover／principal account → users／identity mapping → memberships → 舊新 assignments → 舊新 delegations → 共用 policy → 舊新 sessions。集合按本節 DDL 與 source-hash 清單展開成 runner 的固定完整 relation manifest；包含 roles、permissions、scope rules、priority 及 sponsor／delegation 閉包，不能只鎖已存在的來源 rows。此模式阻止相關 tables 的 INSERT／UPDATE／DELETE 且保留一般 SELECT；只在受控短暫 cutover 持有，正常授權／一般 provisioning 不取全表鎖。

所有本地 locks 取得後，owner transaction-bound client以後續SQL重讀並建立來源集合；舊 writer 若先 commit，其新增／撤銷／deny 必須進入新 source hash，與 prepare 不同就 409、零部分寫入。跨 owner 的 active mapping／typed／authority／grants／Platform state 在鎖後**同一 SQL statement**經既有 versioned read contracts 擷取為不可變的交易內輸入；不將數次 READ COMMITTED 查詢拼成同一 provider snapshot，read contract 不使用 writer 或 VOLATILE 旁路。此後只使用這份 producer capture 與已鎖定的本地來源比較 hash、做等價判定、寫 principal account／ACL／barrier、撤銷 UID sessions、標記 principal_active、寫 receipt 後 commit。跨 owner 在 capture 之後仍可變更，其 current admission／epoch／grants 由後續 request snapshot 拒絕；cutover 不複製 OrgMaster grant、不發登入 session，也不承諾 producer 到 commit 之間不能變更。

任何 deadlock／lock timeout／DB error 都整筆 rollback，沿既有 2 秒 lock／5 秒 statement 預算，不無限延長等鎖。未知結果以原 operation_id／input_hash 在新 transaction 查 receipt；成功時不重跑 source preflight，無成功紀錄才用原 input 做完整 preflight。已正常更新 ACL、停用帳戶或切換 authority，不讓 replay 成為新的授權寫入。來源漂移需重新 prepare；新 input 用新 operation ID。commit 後發布外部 receipt 失敗從 DB 結果重建，不重做切換；交易內無 HTTP／GCS／跨 owner writer lock。

065對舊`user_role_assignments`、`approval_delegations`、mapping／`auth_identities`安全欄位、`users`的role/status/lifecycle/system-role安全欄位、舊`account_session_records`新UID session寫入加DB fence：涉及principal_active就拒絕舊DML。`user_company_memberships`的有效domain修改須經principal-aware命令驗actor、遞增profile_version並撤銷該principal sessions；不能在新app驗證後被舊writer繞過。所有舊runtime對共用policy表的直接DML收斂至既有permission editor所用的principal-aware owner函式；角色允許／拒絕仍按既有管理權限，不能只因掌握principal ID即授權。新命令在函式內寫資料，不用可由caller設定的GUC／skipFence參數；runtime無owner／disable-trigger權，舊binary也無法自行解除fence。新principal ACL管理與本地lifecycle writer繼續使用既有UI/API路徑，handler驗principal管理權限，資料writer只寫新安全欄，display user.role不回流。DB function不新增跨app API。065先建立相容物件／fence；principal_active才啟用逐帳戶限制。共用policy的直接DML收斂由首次cutover的migrator transaction執行REVOKE，必須已部署且僅服務principal-aware writer baseline後才切換；migration先於candidate時不會提前破壞現有legacy writer。owner command完成後舊binary即使仍存在也不能改共用policy。這是實作順序，不新增人類核准步驟。

舊 writer fence 的判定也不能沿用等鎖前的 marker：RC writer 的 VOLATILE fence 在取得 table／target lock 後以新 SQL 讀 cutover 狀態；涉及已 active 的 profile 則拒絕。尚有未收斂的 RR／SERIALIZABLE 舊 writer 時，fence 明確拒絕該不支援模式，不能用其舊 snapshot 證明仍是 legacy。P03／P08 在同一原案例測「apply 已開始等待鎖，舊 RC writer 新增 deny／assignment 後 commit → source hash 拒絕」及「cutover 先 commit，先前等待的舊寫入醒來 → fence 拒絕」；單測更新已存在 row 不足。缺 manifest relation、無法取得完整鎖均回失敗，不縮小清單繼續。profile 身分 link 不提供日常重新指派；必要修正仍走 owner command／source 重驗／profile_version 與 session 失效，不刪歷史 FK 或復活 UID。

### 單一授權讀點與 transaction 使用規則

這是 B 人類 request 的現行契約，取代下方歷史「先驗 current epoch，再開權限 snapshot」的順序。`auth-async.ts` 目前先建立 session context，`numbering-permission-async.ts` 才開 RR transaction；不可把該分段流程原樣搬入 principal 模式並聲稱一致快照已涵蓋 session。

1. 交易外只做 token 驗簽、exact issuer／audience／schema、固定 claims 解析與輸入形狀檢查。verified proof 仍帶原 session ID、principal／pair、epoch、auth time、lifecycle／profile stamps 及 assurance policy hash；此私有 request context 不序列化，不能縮成 principal ID 後省略撤銷查核。
2. 純授權／讀取使用同一 `REPEATABLE READ READ ONLY` client，讀 local session registry、Platform principal state、OrgMaster active pair／typed、principal account／profile、assurance、selected authority／grants 或 principal ACL、policy 及 resource/membership。成功後才產生該 request 的 verified authorizationActor；全部 permission／batch 與 domain predicate 共用此資料讀點。`authenticated_domain` 同樣重驗可變安全狀態，只是不要求新增 permission。
3. 人類 command 的 owner write transaction 將同一 evaluator 核心、resource/CAS、receipt 與 mutation 放在一起；principal 路徑最低為 `REPEATABLE READ READ WRITE`，已要求 SERIALIZABLE 的命令與 provision 保持原較強模式。`platform-command-service.ts` 目前的 `{serializable: undefined}` 會落預設 RC，不能直接沿用後聲稱多次 SELECT 是同一 snapshot；以既有 `isolationLevel` 選項明確設定，caller 已持有 transaction 時驗證模式，不巢狀開交易。不要求所有業務寫入一律升為 SERIALIZABLE，也不改未遷移的 legacy／workload 模式。不得使用另一個已 commit 的 RR allow 或遺失 authorizationActor 後以 pdm_user_id 重建身分；資源寫入競態仍由該 writer 的鎖／CAS 處理。

   **目前本機封鎖點。** 已確認 v2 actor stamp 過去可在前一授權交易完成後傳入預設 RC 命令；它只證明曾驗證，不能代表本次 mutation 的權限。未出貨的 command service 現已提供同一 RR／SERIALIZABLE 寫入交易內重驗 v2 token、session／epoch、active profile、workspace permission、actor、cutover，再執行 command／outbox；server-owned route policy 另與實際 HTTP method、path、session cookie 綁定，GET grant 不能放行 mutation。缺完整 `principalRequest`、權限拒絕或 actor 混版即拒絕。現有業務 route 尚未接入這個上下文，v2 人類命令仍以 `PLATFORM_PRINCIPAL_COMMAND_CONTEXT_REQUIRED` 停止。下一步須逐 route 接入可信 resource guard、完成正常與撤銷競態證據，再解除實際使用路徑的封鎖；本段不是 Production 發布就緒證據。
4. decision snapshot 的建立點是該 transaction 第一個會取得 snapshot 的資料 statement；不能把 token 驗簽、BEGIN 或等鎖完成誤稱為同一時刻。撤銷先 commit、後取得 snapshot 必須拒絕；先取得完整舊 snapshot 的已開始請求可依既有規則完成，不承諾事後取消。RR 寫入遇 40001 整筆 rollback，沿既有錯誤通道由新 request／同 operation 重試；不為它新增無限自動重試。現有 SERIALIZABLE 自動 retry 每次都從原 verified proof 重新讀全部狀態／判定，不能閉包重用上一 attempt 的 allow／domainContext。callback 建立 session 仍綁來源 proof stamp，禁止用 current epoch 重新蓋章。
5. 缺列、狀態不符或 producer 不可用使用既有 401／403／503 分類；不借另一連線補讀。P04／P07 補 signature 後、首個資料 read 前完成 logout／local revoke／lifecycle update；P06／P08 補 writer retry 期間撤權、同一 command actor 不變且重新評估。既有 D121-PG-01／02 僅證明原 authority/grant race，不能算成新增 session-state race 已 PASS。

授權交易的資料流固定為 `verified local session → current epoch／active principal → BEGIN REPEATABLE READ READ ONLY → 再確認同一 actor 的 active principal → 唯一 authority → 該來源 grants 或 local ACL → server-side resource／membership／priority → 所有 permission 結果 → COMMIT`。已驗證 session 的 `localPrincipalId` 必須等於 local user ID、`companyId` 等於 user `company_id`，且 local account／session registry／lifecycle version 均有效；transaction 內再讀的 active principal 必須與 session 的 issuer、subject、principal、employee 完全一致。HTTP、batch、內部命令一律從這個 verified context 取得 actor，不能由 `user.role` 或 client 欄位合成。

第一個 DB read 建立 PostgreSQL `REPEATABLE READ` 快照，交易內 `transaction_timestamp()` 固定單一 `decisionAt`；grant half-open 有效期 `[validFrom, validUntil)` 與 legacy ACL 有效期共用此時間，batch 不逐項重新讀 `Date.now()`。Priority 為同交易唯一 active row；其缺失／重複／格式錯誤一律拒絕。短交易不得包含外部 HTTP、檔案傳輸或 response streaming。switch／logout commit 後才開始的 request 必須看到新狀態；已在 commit 前取得快照者可按舊快照完成。任何 producer／DB 逾時、零筆／雙筆、混版、scope 不明、priority 缺失或顯式 deny 皆拒絕；`legacy_authority` 僅是同快照選定的合法來源，不是錯誤 fallback。不得逐 permission 再開交易。隔離 PostgreSQL D121-PG-01／02 已證明前後請求分別使用完整舊快照與新權威狀態。

使用者已明示舊架構無保留必要。完成全 cohort principal 化、舊 session 到期／撤銷、owner rollback 觀察及原 L4 分母後，直接刪除 legacy authority runtime branch、UID→`pdm_user_id` 授權 resolver、`pdm:*` 合成、舊命令轉接與 Firebase 邀請權限入口；只保留歷史資料與版本化 receipt 的唯讀稽核能力。切流前若仍有未遷移帳號，暫時 fence 僅保護受控回復，不能成為長期完成條件。

現行 owner workflow 已可依同一 source-frozen capsule 執行 `prepare → build → migrate` 並在 `migrate` receipt 通過後停住；這三步不建立 candidate、不 patch service template／entrypoint、不切 traffic。OrgMaster provider readback 與 v4 consumer 發布完成後，續用同一 capsule 的 `candidate → entrypoint → verify → decision → activate → canonical → finalize`，不得重建不同 source 的 migration bundle。暫停期間須保留 control／receipt，於 capsule deadline 內完成後續步驟；過期時重新 source-freeze 與完整 baseline readback，不把過期 capsule 當授權。

所有 principal v2 request 的權限評估均在同一已驗證 PostgreSQL snapshot 讀取 `ai_pdm_contract.v_application_role_catalog_v1`，核對 contract／application／active version／catalog hash／九個 role definition hash 與順序後才使用 v4 artifact；不再依 permission code 在 v3、v4 兩套 runtime catalog 間選擇。owner 發布順序為 source-frozen migration runner 獨立套用 065／066（不切 AI-PDM traffic）、OrgMaster v4 consumer provider readback／release、AI-PDM v4 candidate／traffic。若 owner profile 不支持無 traffic 的 migration 執行，先補其精確契約及證據；不得改用短暫不一致的雙目錄 runtime。這是新 principal 路徑的單一目錄，不代表舊 v1 session 已退役。舊登入與 `pdm:*`／Firebase UID runtime bridge 僅作切流期間的受控回復基線；在既有 profile、session、outbox、route、資料一致性及 L4 分母都完成後，直接移除舊授權入口與自動 mapping 寫入，不將它們變成永久相容層。歷史 `pdm_user_id`、UID alias、receipt 與業務 FK 保留作資料與稽核識別，不能重新成為 security subject。

此後 v2 reviewer selection 與一般 permission 使用同一 `requirePublishedPrincipalCatalog`，並在 caller 的交易快照中驗證；role capability UI／change feed 只引用 v4 catalog。v2 command 在 cutover marker 仍為 `legacy_compatible` 時直接拒絕，不會走歷史 mapping；正式 PostgreSQL 命令缺少明確 actor metadata 時不合成 `pdm:*`，即使 caller 自稱 `system` 亦然。SQLite fallback 只保留作隔離本機 fixture；正式 cutover 後將連同 v1 命令轉接一起移除。

舊 canonical command 的 PostgreSQL 路徑已停止按 request 自動建立 organization mapping；其 actor 若已 `principal_active`，在鎖定 receipt 或執行業務副作用前回 410，不能從舊 v1 route 寫入。缺 marker 或未知狀態回 503，只有明示 `legacy_compatible` 才能繼續；這修正了「無列仍執行」的缺口，聚焦 23／23、typecheck、scoped ESLint PASS。未切換帳號的舊路徑暫時只能讀取既有 mapping；若 mapping 缺失則拒絕，不能在請求中補建。此負面 fence 只服務過渡期與 v1 回復，不是新 principal 授權的相容橋，切流收斂後整段刪除。

歷史 Firebase 邀請的撤銷只修改 AI-PDM 本地 invitation、legacy mapping／account 狀態，先由 065 資料庫 fence 拒絕已 `principal_active` 的 profile，再撤銷本地邀請。AI-PDM 不再從此入口停用、撤銷 refresh token 或刪除共享 provider 身分；Shared Identity 的 provider lifecycle 由 Platform owner 處理。這避免舊應用指令破壞其他系統仍需使用的 canonical principal alias。全體切換後移除整條舊邀請 runtime 路徑，歷史紀錄留作不可授權的稽核資料。
