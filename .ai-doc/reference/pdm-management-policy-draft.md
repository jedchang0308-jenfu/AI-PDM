# 鉦富機械 PDM 使用者管理辦法

狀態：Proposed Baseline  
版本：2026-07-09
文件負責人：CTO / PDM Admin
適用對象：營銷、研發、採購、生產、品管、主管、PDM 管理員
適用範圍：新產品開發、重大改良、圖面送審、BOM 管制、技術移轉、設計變更、正式發行與舊版追溯

本文件是給 PDM 使用者看的作業規則。使用者不需要理解系統程式怎麼寫，只需要知道：什麼時候要開案、圖號與料號怎麼用、版次怎麼判斷、哪些資料要送審、誰可以核准、什麼版本可以拿去生產或對外使用。

管理原則：PDM 不是單純放檔案的地方，而是用來保護圖面、BOM、驗證紀錄、技術移轉與設計變更的共同依據。任何正式生產、採購、製造交接、安裝、維修與外部分享，都應以 PDM Released 版本為準。

## 1. 先看這張表：我應該做什麼

| 角色 | 主要工作 | 必須注意 |
| --- | --- | --- |
| 營銷 / 現場人員 | 提供客戶需求、現場限制、使用問題與回饋 | 需求要具體，不能只口頭說明；會影響設計者需留下紀錄 |
| 研發 / 設計人員 | 建立圖面、BOM、驗證資料與送審資料 | 開發中用小版次，正式發行後才用大版次 |
| 採購 | 依 Released BOM 與規格採購 | 未 Released 或 Obsolete 資料不得作為正式採購依據 |
| 生產 | 依 Released 圖面、BOM、SOP、檢驗表製造 | 小版次不得直接流入正式生產，除非主管核准有條件試用 |
| 品管 / 檢驗 | 依 Released 檢驗標準與試車表確認品質 | 檢驗紀錄要能追溯到圖號、料號、版次 |
| 主管 / 審核者 | 判斷是否核准、退回、技術移轉或設變結案 | 核准前要確認需求、風險、驗證與文件已齊備 |
| PDM Admin | 維護管理辦法、權限、資料完整性與異常處理 | 不直接替代設計審查；只管理系統與制度一致性 |

## 2. 產品案件先分級

鉦富機械是低量、多客製、重機械設備公司，不應把每張訂單都當成完整新產品開發案。開案前先判斷案件類型，避免流程過重，也避免重大風險沒有驗證。

| 類型 | 什麼情況算這一類 | 管理方式 | 常見例子 |
| --- | --- | --- | --- |
| A 類：成熟客製案 | 既有成熟產品，只調整尺寸、材質、配置或安裝條件 | 完成需求確認、設計審查、圖面/BOM、FAT/SAT 即可 | 油水分離槽尺寸調整、攔汙柵材質變更 |
| B 類：重大改良案 | 結構、馬達、刮泥、浮除、控制邏輯、維修方式或製程方式有重大變更 | 由專案管理軟體規劃驗證活動；PDM 留存變更風險與驗證證據 | 改馬達規格、改刮除機構、改清理方式 |
| C 類：全新平台案 | 新機型、新平台、新處理原理、新市場或新外銷規格 | 由專案管理軟體管制專案進度；PDM 管制驗證證據與技術移轉 | 新型加壓浮除設備、外銷版標準機 |

若無法判斷類型，先由研發、營銷、生產與主管共同確認。分類錯誤會造成兩種風險：把簡單客製案做得太慢，或把重大改良案太快推進生產。

## 3. 一張圖從開發到正式使用的狀態

| 狀態 | 使用時機 | 版次範例 | 可以拿來正式生產嗎 |
| --- | --- | --- | --- |
| 開發中 | 新產品開發、概念驗證、草案設計 | `0.1 -> 0.2 -> 0.3 -> ... -> 0.11` | 不可以 |
| 候選移轉 | 必要驗證證據已完成，準備交給生產 | `0.x` | 原則上不可以，除非主管核准試用 |
| 正式發行 | 技術移轉完成，可作為正式依據 | `1` | 可以 |
| 設變中 | 已發行產品正在修改、驗證或補正 | `1.1 -> 1.2 -> 1.3 -> ... -> 1.11` | 不可以 |
| 設變完成 | 設變驗證與審查完成，正式取代前版 | `2` | 可以 |
| 舊版保留 | 已被新版取代，但仍需查詢歷史 | `Obsolete` | 不可以 |

使用者只要記住一件事：小版次代表開發中、驗證中或設變中；大版次代表已完成技術移轉或設計變更結案。

## 4. 版次怎麼填

- `revision` 是版次欄位，送審時必須有值。
- 系統依工程圖資料及編號管理辦法 4.1 原則自動帶入預設版次，使用者可依圖紙修訂欄編輯。
- 版次格式一律不加 `V`；欄位名稱「版次」本身就代表 Version。
- 系統不得接受 `V1`、`V0.1`、`A/B/C`、`R01/R02` 或其他英文字母版次格式。
- 發行區使用大版次整數，例如 `1`、`2`、`3`。
- 技術移轉前，所有需要圖號管控的圖面使用小版次：`0.1 -> 0.2 -> 0.3 -> ... -> 0.11 -> ...`。
- 技術移轉完成後，候選小版次轉為第一個大版次：`0.x -> 1`。
- 技術移轉後若發生設計變更，先進入小版次：`1.1 -> 1.2 -> 1.3 -> ... -> 1.11 -> ...`。
- 設計變更完成並經核准後，轉為下一個大版次：`1.x -> 2`。
- 後續依同樣規則循環：`2.1 -> 2.2 -> ... -> 3`。
- 小版次必須當成文字或分段數字理解；`0.11` 是第 11 次小版，不是 Excel 小數，也不是 `0.1`。

使用者常見判斷：

| 情境 | 應使用版次 |
| --- | --- |
| 新產品第一次畫圖 | `0.1` |
| 開發中修改第二次 | `0.2` |
| 開發中修改第十一版 | `0.11` |
| 技術移轉完成 | `1` |
| Rev1 正式發行後要設計變更 | `1.1` |
| 設變中補正到第十一版 | `1.11` |
| 設變完成並核准 | `2` |

## 5. 主根號、料號、圖號規則怎麼用

主根號、料號與圖號不是同一件事。使用者查資料時可以從任一號碼進入，但判斷責任要分清楚：主根號負責把同一設計主題的圖與料聚合起來，料號負責 BOM 與用料身分，圖號負責圖面與圖檔身分。

### 5.1 編碼原則

鉦富機械新建 PDM 資料採用 V3 編碼規則。歷史 v1/v2 資料仍可查詢與追溯，但新建資料以本章格式為準。

| 號碼類型 | 格式 | 例子 | 使用者要知道的意思 |
| --- | --- | --- | --- |
| 主根號 `root_code` | `{英文字母}{四碼流水}` | `A0001` | 同一設計主題或可追溯設計家族的聚合入口 |
| 料號 `part_number` | `{主根號}-P{兩碼流水}` | `A0001-P01` | 可進 BOM、採購、成本、庫存與製造用料的零件身分 |
| 製造圖號 `drawing_number` | `{主根號}-M{兩碼流水}` | `A0001-M01` | 製造圖類別的圖面身分 |
| 參考圖號 `drawing_number` | `{主根號}-R{兩碼流水}` | `A0001-R01` | 參考圖類別的圖面身分，不可作為製造依據 |

編碼限制：

- `A-Z` 只代表容量區段，不代表客戶、產品線、專案、部門、生命週期、圖面類型或任何商業分類。
- `P` 只代表料號。
- `M` 只代表製造圖類別，不代表已核准、已發行或目前可製造。
- `R` 代表參考圖，任何狀態下都不得作為製造依據。
- `0000` 與 `00` 為保留碼，不得使用。
- 主根號、料號與圖號都必須以文字處理；Excel、CSV、匯入、匯出與報表不得把這些號碼當數字處理。

### 5.2 三個號碼的唯一真相來源

| 號碼 | 系統唯一真相來源 | 代表哪些資料的準確來源 | 不代表什麼 |
| --- | --- | --- | --- |
| 主根號 `root_code` | `part_roots.root_code` | 核心品名、設計主題、設計家族、圖料關係群組、主圖/主料關聯入口 | 不代表專案號、訂單號、客戶號、設備序號，也不取代圖號或料號 owner |
| 料號 `part_number` | `part_numbers.part_number` | 料號、品名、料件類型、BOM 用料、採購用料、成本用料、庫存與製造用料身分 | 不代表圖面是否可製造，也不取代圖號版次 |
| 圖號 `drawing_number` | `drawing_numbers.drawing_number` | 圖號、圖面用途、製造圖/參考圖分類、圖面生命週期、圖面附件、圖面版次與圖檔追溯 | 不代表料件是否可採購，也不代表同主根底下所有料號都可用 |

管理邊界：

- 主根號是聚合入口，不取代圖號與料號 owner。
- 圖料關係由圖料關聯資料管理，不能只靠號碼字串猜測。
- 送審後的審核證據以 submission snapshot 為準，不會因後續主資料變更而自動改寫。
- 若主根號、料號、圖號或送審 snapshot 互相不一致，應先回到各自唯一真相來源查證，不得用人工記憶或檔名猜測。

### 5.3 圖號與料號使用規則

- `drawing_number` 為必填欄位。
- `drawing_number + revision` 必須唯一，系統不可接受重複送審。
- 圖號主體不因版次改變；改版時改版次，不改圖號主體。
- `part_number` 為必填欄位。
- `part_number` 代表 item master identity，同一料號不得指向不同實體零件。
- 同一零件改版時應沿用料號並建立新 revision；不同零件不得共用料號。
- Released 紀錄必須可追溯，不可因後續 revision 建立而被覆蓋或刪除。
- 新 revision 成功 Released 後，系統才更新目前有效版本，舊 Released revision 轉為 `Obsolete`。

實務判斷：

| 問題 | 原則 |
| --- | --- |
| 同一設計主題下新增第二個零件 | 沿用主根號，新增下一個料號，例如 `A0001-P02` |
| 同一設計主題下新增第二張製造圖 | 沿用主根號，新增下一個製造圖號，例如 `A0001-M02` |
| 只是同一張圖修改尺寸 | 沿用圖號，增加 revision |
| 是不同設計主題、主要功能或製造基準不同 | 建立新主根號 |
| 是不同零件或用途不同 | 建立新料號 |
| 只是參考資料或安裝參考 | 使用參考圖號，例如 `A0001-R01`，不得當製造依據 |
| 舊版已經被新版取代 | 查得到，但不得作為正式製造、採購或外部分享依據 |

## 6. 研發驗證證據怎麼管理

PDM 不管理專案階段；專案進度、里程碑與階段名稱由專案管理軟體負責。PDM 只管理「設計可行、現場可用、公司做得出來」所需的受控證據，以及這些證據是否足以進入技術移轉。

| 驗證主題 | 使用者要回答的問題 | 主要參與角色 | 需要留下的紀錄 | PDM 管制結果 |
| --- | --- | --- | --- | --- |
| 工程可行性 | 核心機構、材料、零組件、控制概念可不可行 | 研發、生產、必要時採購 | 測試照片、試驗結果、問題清單、初步風險 | 證據受控並可追溯 |
| 設計符合性 | 完整設備設計是否符合客戶需求與現場條件 | 研發、營銷、現場、生產、品管 | 設計輸入、處理量、安全性、維修性、圖面/BOM 檢查 | 審核結果與補件狀態受控 |
| 製程可行性 | 公司能不能穩定做出、裝好、交付與維修 | 生產、研發、品管、採購 | 焊接、組裝、治具、試車、檢驗點、供應商與工時紀錄 | 移轉前必要證據齊備 |
| 技術移轉 | 生產是否能依文件正式製造 | 主管、研發、生產、品管、營銷或現場 | 技術移轉檢核表、正式圖面、BOM、SOP、檢驗表 | `0.x -> 1` |

A 類成熟客製案仍要有需求確認、圖面/BOM、製造與檢驗依據。B 類與 C 類不得只靠經驗口頭放行。專案管理軟體中的階段變更不會自動改變 PDM 資料狀態。

## 7. 技術移轉何時可以做

技術移轉不是「檔案上傳完成」，而是公司確認這個產品或重大改良已經可以交給生產穩定執行。

技術移轉前至少確認：

1. 正式圖面已審查，所有受控圖面停留在同一候選小版次。
2. BOM 已確認，料號、材質、規格、供應商來源清楚。
3. 專案所要求的必要驗證紀錄已完成，重大風險已有處置。
4. 試車、檢驗、安裝、保養重點已文件化。
5. 生產部確認可製造。
6. 營銷或現場人員確認符合客戶使用情境。
7. 總經理或授權主管核准技術移轉。

技術移轉完成後，受控圖面、BOM、SOP、檢驗表由 `0.x` 轉為 `Rev1` 或大版次 `1`，並進入正式可生產狀態。

## 8. 設計變更什麼時候要開 ECO

正式發行後，只要變更會影響製造、採購、安裝、維修、品質、安全、成本或客戶承諾，就要開立 ECO。

| 影響項目 | 是否需 ECO |
| --- | --- |
| 尺寸、材質、結構、焊接方式 | 需要 |
| 馬達、泵浦、電控、感測器規格 | 需要 |
| 處理量、效率、安全性、維修方式 | 需要 |
| BOM、供應商替代、成本結構 | 需要 |
| 檢驗標準、試車方法、安裝方式 | 需要 |
| 純錯字、格式、註解，且不影響製造與檢驗 | 可走文件修正，不升大版次 |

設計變更流程：

`ECO 立案 -> Rev1.1 -> 驗證 -> Rev1.2 -> 補正 -> Rev1.x -> 設變審查 -> Rev2 正式發行`

未完成設變的小版次不得直接流入正式生產。若因急案必須使用，需由總經理或授權主管核准有條件放行，並記錄風險、使用專案、補救措施與追蹤期限。

## 9. 送審、審核與發布怎麼走

| 步驟 | 使用者動作 | 系統狀態 | 重點 |
| --- | --- | --- | --- |
| 建立送審 | 研發或負責人上傳圖面、BOM 或相關文件 | Pending | 資料不完整不要送審 |
| 審核 | 有權限主管核准或退回 | Approved / Rejected | 退回後需補正再送 |
| 發布 | 審核通過後發布正式版本 | Released | Released 才能作為正式依據 |
| 發布失敗 | 發布過程發生錯誤 | ReleaseFailed | 需由 PDM Admin 或負責人排除 |
| 舊版保留 | 新版 Released 後舊版轉為歷史版 | Obsolete | 可查詢，不可當正式依據 |

審核規則：

- Engineer 可建立送審，但不可 approve 或 reject。
- R&D Manager 與 Admin 可依角色權限 approve 或 reject。
- `approval_required=1` 代表一位有權限審核者核准後即可發布。
- `approval_required=2` 代表兩位不同審核者都必須核准後才可發布；同一人不得核准兩次。
- 若任一審核者 reject，該筆送審轉為 Rejected，不再進入發布流程。
- 正式上線前，公司需確認預設採用 `approval_required=1` 或 `approval_required=2`。

## 10. 檔案與表單怎麼準備

每筆送審至少需包含一個檔案。使用者上傳檔案前，應確認檔名、圖號、料號、版次與內容一致。

支援檔案類型：

| 類型 | 用途 |
| --- | --- |
| `pdf` | 主要預覽與審核格式 |
| `dwg` | CAD 圖面交換或加工參考 |
| `sldprt` | SolidWorks 零件 |
| `sldasm` | SolidWorks 組合件 |
| `slddrw` | SolidWorks 工程圖 |
| `other` | 其他必要附件 |

新產品開發與設計變更先控制在 7 張表單以內：

| 表單代號 | 表單名稱 | 使用時機 |
| --- | --- | --- |
| `NPD-01` | 新產品開發立案表 | A/B/C 分級與開案 |
| `NPD-02` | 設計輸入與需求確認表 | 客戶需求、現場條件、限制條件 |
| `NPD-03` | 研發驗證紀錄表 | 工程、設計、製程驗證證據 |
| `NPD-04` | 技術移轉檢核表 | `0.x -> 1` 前 |
| `NPD-05` | 圖面 / BOM 版次管制表 | 圖面、料號、BOM 版次同步 |
| `NPD-06` | 設計變更申請表 ECO | 正式發行後變更 |
| `NPD-07` | 產品正式發行核准表 | 大版次正式發行 |

## 11. 發布與同名檔案規則

- Pending 送審可被核准並進入發布流程。
- Released、Rejected 或 Obsolete 送審不可再次 approve。
- Release failure 必須記錄為 `ReleaseFailed`，並保留錯誤訊息供追查。
- 成功 Released 新 revision 後，同一 item 的舊 Released revision 會自動轉為 `Obsolete`。
- Released duplicate filename policy：不同 item 的 Released 同名檔案仍採用「禁止發布並回錯誤」。
- 同一 item 進版時可沿用相同檔名；新版 Released 成功後舊版會轉為 Obsolete，不視為跨 item 同名衝突。
- 若 Released 區已存在不同 item 的同名檔案，系統必須 blocked the release，不可覆蓋既有 Released 檔案。

使用者的實務做法：如果檔名相同但其實是不同零件或不同設備，先改正圖號、料號或檔名，不要硬送審。

## 12. 權限與責任

| 權限項目 | 預設規則 |
| --- | --- |
| 閱讀管理辦法 | 所有已登入使用者可閱讀 |
| 編輯管理辦法 | 只開放 Admin |
| 建立送審 | Engineer 或授權角色 |
| 核准 / 退回 | R&D Manager 或 Admin |
| 正式技術移轉 | 總經理或授權主管核准 |
| 有條件試用小版次 | 總經理或授權主管核准並留下紀錄 |

管理辦法修改後，應同步作為研發、品管、審核、PDM 操作與 AI 助手回答的共同依據。若政策文件與系統行為不一致，需視為流程或系統缺陷處理。

## 13. AI 助手使用限制

- AI assistant is read-only。
- AI 可協助查詢管理辦法、pending reviews、dashboard metrics、submission detail、file metadata 與 PDM rules。
- AI 不可 approve、reject、delete、revise、release、publish 或修改任何 PDM record。
- AI 回答管理辦法時必須引用政策資料來源，例如 `.ai-doc/reference/pdm-management-policy-draft.md`。
- 若 AI 回答與管理辦法不一致，以管理辦法與 PDM Released 紀錄為準。

## 14. 與 ISO 9001 的對應關係

截至 2026-07-09，ISO 官方頁面顯示 ISO/FDIS 9001 已進入新版準備階段，預計於 2026 年 9 月發布新版並取代 ISO 9001:2015。因此本管理辦法先依 ISO 9001:2015 的成熟架構與 2026 新版方向建立可落地流程；待 ISO 9001:2026 正式發布後，再校準正式條文號與用語。

| PDM 管理活動 | 對應的品質管理意義 | ISO 9001 對應方向 |
| --- | --- | --- |
| A/B/C 產品分級 | 先判斷風險與流程深度，避免過度或不足管理 | 風險導向思維、營運規劃 |
| 設計輸入與需求確認 | 確認客戶需求、現場條件、法規與公司能力 | 設計與開發輸入、顧客要求 |
| 研發驗證證據 | 用證據確認設計可行、可用、可製造 | 設計與開發控制、驗證與確認 |
| 技術移轉 | 把設計成果正式交給生產、檢驗與交付流程 | 生產與服務提供、產品放行 |
| 主根號、圖號、料號、版次 | 控制設計主題、圖料關係、工程資料與有效版本，避免錯版製造 | 文件化資訊、識別與追溯、設計開發控制 |
| ECO 設計變更 | 正式控管變更影響、驗證與發行 | 變更控制、不符合與矯正措施 |
| Released / Obsolete | 明確有效版本與歷史版本 | 產品放行、追溯與知識保存 |
| 審核權限 | 避免未授權放行或同一人重複核准 | 職責權限、內部控制 |

## 15. 管理員與稽核留存規則

本章給 PDM Admin、主管與稽核使用。一般使用者只需照前述章節操作。

- 系統需保存送審、審核、發布、退回、失敗與 Obsolete 的紀錄。
- 系統需保存每個檔案的 SHA256、檔案大小、原始檔名與 repository 路徑，供追溯使用。
- DB 與 repository 必須保持一致；缺檔、orphan files 或 hash mismatch 都視為品質異常。
- Google Drive release 必須完整成功；若部分搬移失敗，需補償回復或留下可追查紀錄。
- 須製程管制的研發工作區與設計變更工作區使用小版次；無須製程管制的研發工作區與設計變更工作區可不填圖號與版次，發行時仍需圖號與大版次。

## 16. 目前仍需管理層確認的 P0 項目

- 是否排除易混淆字母 `I/O/Q`；目前新建資料採用 `A-Z` 全字母容量區段。
- 歷史 v1/v2 編碼資料的長期顯示、匯入與查詢相容策略。
- 圖號、料號、主根號的手動例外建立權限與審核方式。
- 正式版次是否完全由系統自動產生，或保留受控手動編輯。
- 預設審核模式：`approval_required=1` 或 `approval_required=2`。
- Released 同名檔案長期策略：維持禁止、改成封存舊檔，或允許受控版本覆蓋。
- B 類重大改良案與 C 類全新平台案的 Gate 核准角色。
